# CLAUDE.md

Guidance for Claude Code (and humans) working in this repository. Update it in the same commit as any behavior change.

## Project

Pool session reservation app for GTÜ (Gebze Technical University). One-hour sessions; each session has N lanes with a per-lane capacity. Members pick a lane. Monthly credit system tied to admin-managed membership months. Turkish UI, mobile-first. Sister project of the tennis court app (same stack and conventions).

## Stack

Next.js 15.5 (App Router) · React 19 · TypeScript (strict) · Tailwind CSS · Supabase (Auth, Postgres, pg_cron) · Resend · Vercel (functions run in UTC). Validation with zod.

## Commands

```bash
npm run dev | build | lint | typecheck
```

## Architecture (layers, one direction only)

```
UI (app/, components/)  →  server actions (lib/actions/)  →  data layer (lib/data/)  →  Postgres functions (RPC)
                                     ↘ lib/email (Mailer interface)        ↘ lib/validation (zod)
```

- **Postgres functions are the API.** All reads and writes go through `security definer` functions in `supabase/01_schema.sql`. Tables have RLS enabled, no write grants, and only `profiles` own-row SELECT. Never add direct table access from the app.
- **lib/data/** is the only place that calls `.rpc()`; it maps snake_case rows to domain types (`src/types`). DB errors are raised as short codes (`lane_full`) and surface as `RpcError(code)`.
- **lib/actions/** (`"use server"`): validate input with zod → call data layer with the user's session client → map error codes with `messageFor()` (`lib/errors.ts`) → `revalidatePath`. Actions never trust client-provided identity, names or prices.
- **Admin actions** use `withAdmin()`: app-level check (`getAdminProfile`) + DB-level `assert_admin()` (defense in depth). Every admin DB function writes to `admin_audit_log`.
- **Secret key** (`lib/supabase/admin.ts`) is used for exactly one thing: deleting an auth user after `admin_prepare_delete` authorizes and logs it.
- **Email** goes through the `Mailer` interface (`lib/email/mailer.ts`); templates escape all user text.

## Domain rules (enforced in SQL, mirrored in UI)

- Sessions are generated by `generate_sessions()` (pg_cron daily 21:05 UTC, and after settings change) for today + `booking_window_days` + 7 days. Schedule: weekday/weekend start–end, end exclusive, 1-hour sessions on the hour.
- `book_session`: session not started; date ≤ today + window; lane valid; not closed (session or lane); one active booking per user per session; daily limit; membership row for the session's month; used < credits; lane count < capacity. Locks: user row → settings (share) → session row.
- Credits: `memberships(user_id, month, credits)`. Used = count of `active` bookings in that month. Cancelling (user or admin) refunds automatically. Credits don't roll over. `admin_add_month` uses `settings.monthly_credits`. When `monthly_credits` changes, `admin_update_settings` moves future months (month > current month) that still equal the old default to the new value (never below used); the current month and per-member custom values are untouched.
- `cancel_booking`: own, active, not started, at least `min_cancel_hours` before start.
- Closures: `closures(session_id, lane NULL = whole session)`. Closing cancels affected bookings (`cancelled_by_admin`, reason) and returns them so the action can email members.
- Settings changes are rejected if they would orphan future bookings (lane removed / capacity below bookings).
- Bookings are never deleted (history + credit accounting). Sessions with bookings are never deleted.

## Time

Server runs in UTC; Turkey is UTC+3. Use `lib/time.ts` (`todayTR`, `addDays`, `weekStart`, …) — never `new Date("YYYY-MM-DD")` math or `getDate()` on the server. SQL uses `tr_today()` / `at time zone 'Europe/Istanbul'`.

## Security rules (see SECURITY.md)

1. Identity comes from `auth.uid()` in SQL, never from arguments.
2. New DB function: `security definer`, `set search_path = public`, raise short error codes, add to the explicit `grant execute ... to authenticated` list (everything else stays revoked).
3. New admin DB function: start with `assert_admin()`, end with `admin_log(...)`.
4. Validate every action input with zod; return generic messages for unknown errors; log details server-side only.
5. Escape user text in emails (`escapeHtml`). No `dangerouslySetInnerHTML`.
6. Auth messages must not reveal whether an account exists.
7. Redirect targets must be same-site paths (`safeNext` in `app/auth/callback/route.ts`).
8. Never commit secrets; `.env.local` is gitignored.

## UI

Palette in `tailwind.config.ts` (deep, water, lane, rope, mint, line, mist). Fonts: Barlow Condensed (display: times, lane numbers, counts) and Atkinson Hyperlegible (body). Signature element: `.lane-rope` divider between lanes and per-swimmer occupancy segments. Keep everything else quiet. Visible focus, reduced-motion respected.

## Database changes

Edit `supabase/01_schema.sql` as the source of truth, apply the change in the Supabase SQL Editor, then re-dump with `pg_dump --schema-only --schema=public --no-owner` if you need to verify drift.

## Workflow

- Never push to `main`: it is protected (PR required, CI check "Tip, lint, build" must pass). Work on a branch, open a PR.
- CI (`.github/workflows/ci.yml`) runs `npm ci`, typecheck, lint, build, `npm audit --omit=dev --audit-level=critical`. Keep it green and secret-free.
- Vercel deploys `main` to production and every PR to a preview URL.
- Dependabot opens grouped minor/patch PRs only; major upgrades are ignored on purpose and done deliberately on a branch.
- SQL changes ship as a new `supabase/0N_*.sql` migration run manually in Supabase before merging code that depends on it; mirror the change in `01_schema.sql`.
